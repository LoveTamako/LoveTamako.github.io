# 软件开发环境详解：DEV、SIT、UAT、PROD

一套代码从开发到上线，要依次经过几种职责完全不同的运行环境。划分环境的目的不是"多跑几遍"，而是把不同性质的风险分开暴露：写得对不对、连起来对不对、业务认不认、真实流量扛不扛得住。

业界常见的划分是四类：DEV、SIT、UAT、PROD。它并非出自某一部标准，也找不到明确的提出者，而是长期实践形成的约定俗成

## DEV：开发环境

**定位**：开发者写代码、调代码的地方，通常就是本地环境。

本地环境追求的是**反馈速度**：代码可以随意改、随时回滚，服务可以随时重启，数据库可以随时清空重建。代价是本地环境往往缺少真实依赖，所以一般会配套本地数据库，或者用 Docker Compose 把 MySQL、Redis 一并拉起来。需要注意的是，调试用的临时代码、打印日志不要顺手提交进版本库。

## SIT：系统集成测试环境

**定位**：把多个服务、中间件和外部依赖真正部署到一起，验证"各自能跑"之后"连起来还能不能跑"。

SIT 全称 System Integration Testing。它与 DEV 的关键区别是**部署形态**：代码不再是某个开发者本机上的一个进程，而是以接近生产的方式跑在服务器上——服务之间真的走 HTTP 调用，消息真的进 MQ，第三方支付走对方提供的沙箱。因此 SIT 暴露的多是**契约问题**：字段名对不上、时间格式不一致、超时和重试没配、依赖服务没启动。

这一层测的是接口和端到端流程，不是单个功能点。通常由开发提测、测试同学跑冒烟和主流程，通过后才允许进入 UAT。

## UAT：用户验收测试环境

**定位**：由需求方按真实业务流程验收，确认"做出来的东西是不是我们想要的"。自研项目里是业务部门和产品经理，交付型项目里则是甲方。

UAT 全称 User Acceptance Testing。它验证的不是技术正确性，而是**业务符合性**：完整流程能不能走通、权限和审批流是否符合预期、金额和报表算得对不对。所以验收用例应当从业务场景来，而不是从接口或代码分支来。

环境上，配置要尽量贴近生产（同样的中间件版本、超时参数、权限模型），数据则用**脱敏后的生产数据**或按场景造数——把真实数据直接搬进测试环境是合规红线。验收通过时要同时冻结版本基线：哪个制品、哪份配置、哪个数据库变更脚本，后续上线必须用同一份。

## PROD：生产环境

**定位**：真实用户、真实数据和真实流量的环境，也是唯一"出错就有代价"的地方。

前三个环境都可以推倒重来，PROD 不行：改错一行配置，代价就是真实的资损、投诉或数据事故。所以这里的一切变更都按"可能会坏"来准备：有监控告警、能小流量灰度、有变更记录可追溯。也因为它不可试验，权限是四套里最严的——只允许流水线部署，禁止登录服务器改配置或热修代码。

判断一次发布是否合格，不看它在 UAT 跑得多顺，而看生产上出问题时，能不能在几分钟内退回去。

## 完整的环境链路

四个环境不是孤立存在的，而是一条**制品逐级晋级**的流水线：

```text
  开发自测          集成验证          业务验收          线上运行
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│   DEV    │ →  │   SIT    │ →  │   UAT    │ →  │   PROD   │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
     ↑               ↑                ↑                ↑
  每次提交        提测通过          验收签字          发布审批
  快速反馈        接口/流程          业务确认          灰度+回滚
```

**每一级的准入与准出**

| 阶段 | 准入条件 | 准出条件 |
|------|----------|----------|
| DEV → SIT | 本地自测通过，单元测试通过 | 冒烟用例全部通过，无阻塞缺陷 |
| SIT → UAT | 集成测试通过，无严重缺陷 | 回归测试通过，遗留缺陷已评估 |
| UAT → PROD | 业务验收签字，发布方案评审完成 | 灰度观察无异常，监控指标正常 |

关键点在于：**晋级的是同一份制品，而不是同一份源码重新编译一次**。源码每次编译都可能产生不同的结果（依赖版本漂移、构建环境差异），只有制品晋级才能保证"测的是什么，上的就是什么"。

```text
❌ 错误做法
SIT：用源码在 SIT 机器上编译 → 测试
UAT：用源码在 UAT 机器上重新编译 → 测试
PROD：用源码在发布机再编译一次 → 上线

✅ 正确做法
CI 编译一次 → 生成镜像 app:1.8.3
DEV → SIT → UAT → PROD 全部使用 app:1.8.3
```

## 配置和数据

同一份代码要在四个环境里跑起来，差异只能靠配置和数据体现。这两块最容易出问题，也最容易被忽略——很多"测试环境好好的、上线就出事"，根子都在这里。

### 配置

配置要外置。连接地址、超时时间、连接池大小、功能开关，都从环境变量或配置中心里读，不要写死在代码里：

```yaml
spring:
  profiles:
    active: ${SPRING_PROFILES_ACTIVE:dev}
  datasource:
    url: ${DB_URL}
```

密码、密钥不放进代码仓库，交给配置中心的加密项或密钥管理服务。除此之外还有两条经验：

- **别在业务代码里判断环境。** `if ("prod".equals(env))` 一旦写下去，环境差异就散进业务逻辑了，分支会越来越多，测试也覆盖不过来。差异用配置表达，业务开关用功能开关（Feature Toggle）
- **别登录服务器改配置。** 手工改出来的差异没人记录，下次排查问题会被误导，改完过一阵谁也说不清当时为什么改

后者就是常说的**配置漂移**：环境之间出现了没被记录的手工修改。典型表现是三个环境的超时、重试、连接池各不相同，但所有人默认它们是一致的。解决办法是把配置也当代码管——纳入版本库、变更走评审、定期比对环境差异。

### 数据

| 环境 | 数据从哪来 |
|------|-----------|
| DEV | 自己造数，或者把外部依赖 Mock 掉 |
| SIT | 按用例造数，要覆盖边界场景 |
| UAT | 脱敏后的生产数据，规模尽量接近真实 |
| PROD | 真实数据，权限最严，禁止外带 |

生产数据往测试环境搬，必须脱敏。而且脱敏之后还要保住两件事：**关联关系**（订单和用户还得对得上，否则业务验收跑不通）和**数量级**（几万行和几千万行的执行计划完全不是一回事）。手机号这类可以保留格式，比如 `138****1234`。

造数本身也是成本。一个完整场景可能要几十张表配合，手工造又慢又容易漏，比较省事的做法是把常用场景（新用户首单、退款流程、跨月结算）整理成数据集，需要时一键导入。
