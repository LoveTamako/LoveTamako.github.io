# 软件开发环境详解：DEV、SIT、UAT、PROD

一套代码从开发到上线，通常需要经过几个不同的运行环境。划分环境并不是为了多跑几遍测试，而是让不同阶段的问题尽早暴露出来：代码本身有没有问题，多个系统能不能正常配合，业务需求是否得到满足，以及上线后能不能稳定运行。

比较常见的环境划分是 DEV、SIT、UAT 和 PROD。它们并不是某项标准中规定的固定流程，而是在长期的软件开发实践中逐渐形成的通用约定。四套环境的差异，本质上是从"自由"到"约束"的递进：越往后，改动成本越高，验证要求也越严。

## DEV：开发环境

**定位：** 开发人员编写代码、调试功能和进行初步验证的环境，通常以本地环境为主。

开发环境最看重的是**反馈速度和调试便利性**。代码可以随时修改，服务可以随时重启，数据库也可以根据需要清理或重建。由于本地环境通常没有完整的外部依赖，可以使用本地数据库，也可以通过 Docker Compose 启动 MySQL、Redis 等服务；暂时无法接入的第三方系统，则可以使用 Mock 模拟接口行为。

需要注意的是，临时调试代码、敏感信息和本机专用的测试配置不要直接提交到版本库。

## SIT：系统集成测试环境

**定位：** 将多个服务、中间件和外部依赖部署到一起，验证它们能否正常协同工作。

SIT 全称 System Integration Testing。它与 DEV 最大的区别在于部署方式和依赖环境：代码不再只是运行在开发人员本机上的独立进程，而是部署到服务器上，让各个服务按照实际的调用方式交互。例如，服务之间通过 HTTP 通信，消息通过 MQ 传递，第三方系统则尽可能接入对方提供的沙箱环境。

SIT 主要用于发现系统集成过程中可能出现的问题，例如接口字段不一致、时间格式不兼容、超时和重试配置不合理，以及依赖服务不可用等。因此，这一阶段关注的是接口交互和完整业务流程，而不仅仅是单个功能能否正常运行。

通常由开发团队完成部署并提交测试，测试人员执行冒烟测试和主流程测试，通过后再进入 UAT。

## UAT：用户验收测试环境

**定位：** 由业务需求方验证系统是否满足实际业务需求。

UAT 全称 User Acceptance Testing。自研项目通常由业务部门或产品经理参与验收，交付型项目则一般由客户或甲方负责。

UAT 关注的不是技术实现是否正确，而是**业务是否符合预期**。例如，完整业务流程能否正常执行，权限和审批流是否符合要求，金额和报表计算是否准确。因此，验收用例应该围绕实际业务场景设计，而不是单纯从接口或代码分支出发。

UAT 的环境配置应尽量贴近生产，包括中间件版本、超时参数和权限模型等。测试数据可以使用经过合规脱敏的生产数据，也可以根据业务场景自行构造，但不能未经授权直接将包含敏感信息的生产数据复制到测试环境。

验收通过后，还应当确定本次发布的版本基线，包括应用制品、配置版本和数据库变更脚本，确保后续上线使用的内容与验收通过的版本一致。

## PROD：生产环境

**定位：** 承载真实用户、真实数据和真实业务流量的正式运行环境。

生产环境与前三种环境最大的区别在于，出现问题就可能影响真实业务。配置错误、服务故障或数据异常，都可能造成资损、投诉甚至数据事故。

因此，生产环境需要严格控制变更权限，并建立完善的监控告警和审计机制。应用部署尽量通过自动化流水线完成，避免直接登录服务器修改配置或热修代码，所有变更都应留下记录。

上线时可以采用灰度发布（例如金丝雀发布）或蓝绿部署，逐步放量验证新版本的运行情况，同时提前准备好回滚方案。一次发布是否合格，不仅要看 UAT 是否通过，还要看上线后能否稳定运行，以及出现问题时能否及时回滚。

## 配置与数据

### 配置

同一份代码需要在不同环境中运行，而数据库地址、第三方接口地址、超时时间等配置又各不相同。因此，这些配置不应该直接写在业务代码中，而应该通过环境变量或配置中心统一管理。

实际项目中，可以使用 Nacos 等配置中心集中管理应用配置。通常为 DEV、SIT、UAT 和 PROD 分别创建独立的 Namespace，各环境使用相同的 Group 和 Data ID 管理对应的配置。这样，同一份应用制品在不同环境中启动时，只需要指定对应环境的 Namespace，即可加载该 Namespace 下相应 Group 和 Data ID 的配置，不需要因为环境不同而修改代码或重新构建。

例如，可以按照下面的方式组织：

```text
DEV Namespace
└── DEFAULT_GROUP
    ├── application.yaml
    └── datasource.yaml

SIT Namespace
└── DEFAULT_GROUP
    ├── application.yaml
    └── datasource.yaml

UAT Namespace
└── DEFAULT_GROUP
    ├── application.yaml
    └── datasource.yaml

PROD Namespace
└── DEFAULT_GROUP
    ├── application.yaml
    └── datasource.yaml
```

其中，Namespace 用于隔离不同环境的配置，Group 用于对配置进行分组，Data ID 则用于标识具体的配置文件。应用启动时，根据部署环境指定的 Namespace、Group 和 Data ID，从配置中心加载对应的配置。

密码、密钥等敏感信息也不要直接放在代码仓库中，应交由配置中心的加密配置或专门的密钥管理服务统一管理，并做好访问权限控制。

除此之外，还需要注意两点：

- **避免在业务代码中判断运行环境。** 不要大量使用 `if ("prod".equals(env))` 这样的分支。环境之间的差异应该通过配置解决，业务功能开关则可以使用 Feature Toggle。
- **避免直接登录服务器修改配置。** 配置变更应通过配置中心统一管理，并保留变更记录，避免不同环境出现未经记录的配置差异。

:::: warning 配置漂移
不同环境的实际配置逐渐偏离预期配置，这种现象称为配置漂移（Configuration Drift）。例如，生产环境原本配置了 5 秒的接口超时时间，但有人手动修改为 10 秒，却没有同步记录或更新配置版本，时间一长，实际配置就可能偏离预期。

解决办法是将配置纳入统一的版本管理和变更流程，通过配置中心集中维护，并定期检查各环境的配置差异。
::::

### 数据

配置决定服务"连到哪里"，数据决定服务"看到什么"，两者缺一不可。各环境的数据来源大致如下：

| 环境 | 数据来源 |
|------|----------|
| DEV | 自行造数，必要时可以清空重建 |
| SIT | 按测试用例造数，覆盖边界场景 |
| UAT | 脱敏生产数据或构造的业务数据，尽量贴近真实场景 |
| PROD | 真实数据，权限最严，禁止未经授权外带 |

生产数据搬到测试环境后，脱敏还需要兼顾两件事：**关联关系**（例如订单和用户之间的关系必须保留，否则业务验收跑不通）和**数据规模**（几万行和几千万行可能产生完全不同的执行计划）。手机号这类敏感字段可以采用掩码或替换等方式处理，例如 `138****1234`，同时保证脱敏后的数据仍能满足测试场景。

此外，测试数据准备本身也是一项成本。一个完整业务场景往往涉及几十张表，手工准备既慢又容易遗漏。比较省事的做法是将常用场景（例如新用户首单、退款流程、跨月结算）整理成数据集，需要时一键导入。

## 总结

DEV、SIT、UAT 和 PROD 分别承担开发、集成测试、业务验收和正式运行的职责，共同组成了一条从代码开发到生产上线的交付链路。

```text
   开发自测          集成验证          业务验收          线上运行
┌──────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐
│   DEV    │ →  │   SIT    │ →  │   UAT    │ →  │   PROD   │
└──────────┘    └──────────┘    └──────────┘    └──────────┘
     ↑               ↑               ↑               ↑
  每次提交          提测通过          验收签字          发布审批
  快速反馈          接口/流程         业务确认          灰度+回滚
```

各环境还需要明确进入和离开的条件，避免测试和发布过程缺少质量门槛：

| 环境 | 进入条件 | 离开条件 |
|------|----------|----------|
| DEV | 开发任务明确 | 单元测试、自测和代码评审通过 |
| SIT | 提测版本部署完成 | 冒烟与集成测试通过，无阻塞性缺陷 |
| UAT | 版本冻结，SIT 遗留缺陷已评估 | 业务验收通过并签字 |
| PROD | 发布评审通过，回滚方案就绪 | 灰度观察期结束，核心监控指标无异常 |

整个过程中，需要保证软件制品和配置的一致性：代码只构建一次，生成的软件制品逐级部署；不同环境通过配置中心加载各自的配置。这样可以减少环境差异带来的问题，让整个发布过程更加清晰、可控。
