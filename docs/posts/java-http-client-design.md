# Java HTTP 调用设计：从基本模型到可靠性架构

## 1. HTTP 调用的基本模型

### 1.1 HTTP 是什么

HTTP（Hypertext Transfer Protocol，超文本传输协议）是一种应用层通信协议，采用请求—响应（Request-Response）模型，定义了客户端与服务端之间如何交换数据。

在实际开发中，无论是前端调用后端、微服务之间相互调用，还是调用第三方系统提供的接口，本质上都是通过 HTTP 请求和响应来完成通信。

本文不打算详细介绍 HTTP 的底层原理，而是重点讨论 HTTP 调用过程中可能遇到的问题，例如如何判断调用结果、如何处理异常，以及如何保证调用的可靠性。最后会结合 Java 代码，介绍一套相对合理的设计方案。

::: info 其他通信方式

HTTP 并不是唯一的网络通信方式。实际开发中，我们还经常会接触到 WebSocket、gRPC 等技术，它们的通信方式和适用场景有所不同：

- **HTTP**：通常采用请求—响应（Request-Response）模型，适用于常见的接口调用和资源访问。
- **WebSocket**：建立连接后，客户端和服务端可以进行双向实时通信，常用于实时消息推送、在线聊天等场景。
- **gRPC**：基于 HTTP/2 实现远程过程调用（RPC），常用于微服务之间的通信。

:::

### 1.2 一次 HTTP 调用的执行过程

从调用方的角度来看，一次 HTTP 调用其实很简单，本质上就是发送一个请求（Request），然后接收一个响应（Response）。

下面以客户端调用服务端接口为例：

```text
          客户端                             服务端
            |                                 |
            | -------- HTTP Request --------> |
            |                                 |
            | <------- HTTP Response -------- |
            |                                 |
```

1. **请求**：客户端根据接口定义构造 HTTP 请求，并将请求发送给服务端。
2. **处理**：服务端接收到请求后进行处理，并将处理结果封装成 HTTP 响应返回给客户端。
3. **响应**：客户端收到响应后，解析 HTTP 状态码和响应内容，获取本次请求的处理结果。

以上就是一次 HTTP 调用最基本的过程。实际开发中，这个过程并不总是能够顺利完成，下面我们就来看看 HTTP 调用过程中可能遇到的问题。

### 1.3 HTTP 调用面临的核心问题

从前面的调用过程可以看出，一次 HTTP 调用主要涉及客户端发送请求和接收响应两个阶段。理想情况下，请求能够正常发送，服务端能够成功处理，并将处理结果正常返回给客户端。但在实际开发中，网络通信可能出现各种异常，导致调用过程无法按照预期完成。

从客户端的角度来看，HTTP 调用主要面临两类问题：

1. **请求发送失败：**客户端可能因为网络异常、DNS 解析失败、连接被拒绝等原因，无法成功建立连接或完成请求发送。这种情况下，客户端可能无法将请求正常发送到服务端；如果请求发送过程中发生异常，也可能无法确定服务端是否已经收到完整请求。

2. **响应接收失败或超时：**客户端完成请求发送后，需要等待服务端处理并返回响应。但由于服务端处理时间过长、网络中断或响应数据丢失等原因，客户端可能无法正常收到响应，最终触发读取超时或连接异常。

需要特别注意的是，客户端没有收到响应，并不代表服务端没有处理请求。服务端可能已经成功完成业务操作，只是响应没有正常返回客户端。这种情况下，客户端无法确定本次调用究竟成功还是失败。

这两类问题看起来比较简单，但会引出调用结果判断、异常处理、超时、重试和幂等等一系列问题。后续章节将围绕这些问题，逐步介绍 HTTP 调用的结果分类和可靠性设计。

## 2. HTTP 调用结果分类

从上面的分析可以看出，HTTP 调用的结果并非只有成功和失败：在通信过程中发生异常或超时时，客户端可能无法确定请求是否已经到达服务端，也无法判断服务端是否已经执行了对应的业务操作。因此，需要引入更细粒度的结果分类。

在给出分类之前，先明确本文的讨论范围：调用结果仅指 **HTTP 调用层的通信结果**，而不是业务操作的执行结果。两者的职责边界如下：

- **调用层**：负责发送 HTTP 请求、接收 HTTP 响应，并判断本次通信过程是否完成。
- **业务层**：结合 HTTP 状态码、响应内容和接口约定，进一步判断业务操作是否成功。

从调用方的角度来看，一次 HTTP 调用可以分为以下三种结果：

| 调用结果 | 含义 | 判断依据 |
|---|---|---|
| COMPLETED | 调用已完成 | 客户端成功接收到完整的 HTTP 响应，不论 HTTP 状态码是多少 |
| FAILED | 请求发送失败 | 能够确认请求数据尚未发送到服务端 |
| UNKNOWN | 调用结果未知 | 无法确认请求是否已经到达服务端，或未能收到完整响应 |

### COMPLETED

当客户端成功接收到完整的 HTTP 响应时，本次调用就可以标记为 COMPLETED。它仅表示请求—响应过程已经完成，既不代表服务端处理成功，也不要求状态码必须是 2xx。

例如，服务端返回 HTTP 200，但响应体中的业务状态码表示操作失败；或者返回 HTTP 500，只要客户端完整收到了响应，都属于 COMPLETED。至于接口处理结果和业务执行结果，则由上层业务逻辑根据 HTTP 状态码、响应内容及接口约定进一步判断。

需要区分的是，HTTP 状态码和 COMPLETED 描述的是两个不同的维度：前者表示服务端的处理状态，后者表示客户端是否完整收到了响应。因此，2xx 不等于调用完成，4xx、5xx 也不等于调用失败——它们只是客户端完整收到的、表示出错的响应，本质上仍然属于 COMPLETED。

### FAILED：请求发送失败

当客户端能够明确证明请求数据尚未发送到服务端时，可以将本次调用标记为 FAILED。例如，DNS 解析失败、TCP 连接被拒绝等发生在请求数据发送之前的异常，通常可以归入这一类。由于能够确认请求没有发出，因此可以确定服务端没有收到本次请求，也就不会因为这次请求执行对应的业务操作。

但需要注意，异常发生在请求发送过程中，并不一定意味着请求发送失败。例如，客户端在发送请求数据时连接突然中断，可能已经有部分数据发送到服务端，也可能尚未发送任何数据。如果客户端无法确认请求数据是否已经发出，就不能直接认定为 FAILED，而应该归入 UNKNOWN。

因此，判断 FAILED 的关键并不是客户端是否发生了异常，而是能否证明请求数据没有发送到服务端。这也是它与 UNKNOWN 最重要的区别。

### UNKNOWN：调用结果未知

当客户端无法确认请求是否已经发出，或者请求可能已经到达服务端，但未能收到完整响应时，应将本次调用标记为 UNKNOWN。例如，请求发送过程中连接中断、请求发送完成后发生读取超时，或者服务端已经完成业务处理，但响应在返回途中丢失，都可能导致这种情况。

以读取超时为例，客户端已经成功发送请求，但在等待服务端响应的过程中超过了预设的超时时间。此时，服务端可能还在处理请求，也可能已经完成业务操作，只是响应尚未返回客户端。客户端只能确认自己没有在规定时间内收到响应，却无法据此判断服务端是否已经执行了请求。

这也是 HTTP 调用中最需要谨慎处理的一种情况。如果将 UNKNOWN 直接当作 FAILED，并立即重新发送请求，就可能导致同一个业务操作被执行多次。因此，UNKNOWN 不能简单地等同于失败，通常需要结合接口的幂等性、业务状态查询等机制进一步确认实际执行结果。

### 三种调用结果的区别

综上，三个状态的核心区别在于客户端对 HTTP 通信过程的确定程度：COMPLETED 表示已经收到完整响应，FAILED 表示能够证明请求数据尚未发送，UNKNOWN 则表示请求可能已经发出，但无法确认通信结果。

需要特别强调的是，**COMPLETED 不等于业务成功，FAILED 不等于业务失败，UNKNOWN 也不意味着业务一定没有执行**。这三个状态只用于描述 HTTP 调用层的通信结果，业务执行结果需要由上层根据具体接口的响应内容和业务规则进行判断。

从后续处理的角度来看，三种结果也有不同的意义。对于 COMPLETED，调用方已经获得完整响应，可以交由业务层解析和处理；对于 FAILED，调用方能够确认请求没有发送，通常可以在排除故障后重新发起调用；对于 UNKNOWN，调用方无法确定远端是否已经执行操作，因此不能直接假定请求失败并进行重试，而需要结合幂等性、状态查询等机制谨慎处理。

### 是否需要自己封装 HTTP Client？

了解了 HTTP 调用结果的分类后，可能会产生一个问题：既然已经有 Apache HttpClient、OkHttp、JDK HttpClient、Spring RestClient 等成熟的 HTTP 客户端，为什么还需要自己封装一层？这些现有框架能否直接提供 COMPLETED、FAILED、UNKNOWN 这样的调用结果？

实际上，主流 HTTP 客户端已经解决了 HTTP 通信中的大部分基础问题，例如连接管理、请求发送、响应接收、超时控制、连接池管理等。它们通常也会提供统一的响应对象和异常体系，供调用方获取 HTTP 状态码、响应内容以及处理通信异常。因此，日常开发并不需要重新实现一套 HTTP 通信框架。

但这些客户端提供的主要是底层通信能力，而不是本文定义的调用结果抽象。不同 HTTP 客户端的 API、异常类型和内部实现各不相同，而且它们通常无法准确判断请求是否已经到达服务端。例如，发生读取超时时，客户端可能已经成功发送请求，但无法确认服务端是否完成了业务操作；即使客户端抛出了异常，也不意味着请求一定没有发出。由于请求是否真正到达服务端属于网络通信过程中的不确定性，HTTP 客户端无法仅凭异常类型就始终准确地判断远端执行情况。

此外，不同应用对调用结果也可能有不同的定义。例如，有的应用将 HTTP 4xx、5xx 视为调用异常，有的应用则希望将其作为正常接收到的 HTTP 响应，交由上层业务逻辑进一步处理。因此，直接使用某个 HTTP 客户端的返回值或异常体系，未必能够满足所有应用的结果判断需求。

基于这些原因，我们可以在现有 HTTP 客户端之上增加一层轻量封装，将不同客户端的响应和异常统一转换为 COMPLETED、FAILED、UNKNOWN 三种调用结果。这样既可以复用成熟 HTTP 客户端提供的通信能力，又可以让上层业务代码使用统一的结果模型，而不必直接依赖具体客户端的 API 和异常类型。

需要注意的是，这种封装并不是重新开发一个 HTTP Client，也不是要保证能够精确识别所有网络异常对应的真实请求发送状态。对于无法明确判断的情况，应当采用保守策略，将其归类为 UNKNOWN，而不是根据某个异常类型简单推断请求一定没有发出。

因此，比较合理的设计方式是：**使用成熟的 HTTP 客户端处理底层通信，在其上增加一层轻量的调用结果封装，由这一层统一处理响应、异常和调用结果分类。** 至于 JSON 解析、业务成功判断、重试、幂等性等逻辑，则根据职责分别交给上层处理，避免将所有功能都堆积到 HTTP 通信封装中。

本文后续将以这三种调用结果为基础，进一步讨论 HTTP 超时、异常处理、重试和幂等性等可靠性设计问题。
